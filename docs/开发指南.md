## 一、项目简介

把 **DeepSeek Harness（DSH）** 打包成可安装到 Android 手机的 App：

- **内核**：`@deepseek-ai/dsh` 0.1.5-rc.1（依赖闭包由 caret 解析到 0.1.5-rc.2），保留插件生态 + RPC API。
- **前端**：DSH 原生界面（`dsh-web-frontend` dist），只做移动端适配，不自研页面。
- **移动端适配**：自由旋转（`fullUser`）+ 触摸优化 CSS（`mobile-patch/mobile.css`）+ 软键盘/回车行为
  （`mobile-patch/mobile.js`，回车换行、Ctrl/Cmd+回车发送）+ 禁双指缩放（viewport 补丁，`inject.sh`）。
- **手机端特色**：Shizuku 特权插件 + 系统能力插件 + **原生控制台**（权限引导 / 解压 / 引擎启停）+
  虚拟屏预览悬浮窗 + 小鲸鱼状态悬浮球。
- **品牌**：DeepSeek Harness，鲸鱼图标（品牌蓝 `accent_brand`，见 `res/values/colors.xml`）。
- **包名**：`com.deepseek.harness`

### 项目原则

1. **页面 = DSH 原生界面 + 移动端适配**：功能全保留，不做自研页面替代。
2. **API Key 不写文件、不打包进 APK**：凭证由使用者在页面里填写，只存本机。
3. **签名密钥（release.jks）不入仓库**：由维护者离线保管。
4. **非必要不动 DSH 内核包**：内核未正式发布、更新很快，壳层（含 mobile-patch 注入）能解决的
   就不动内核；只有涉及用户数据等必要修复才值得做（升级会被冲掉还要重放补丁）。
5. 自由旋转（竖屏/横屏）；品牌只与 DeepSeek Harness 相关。

### 开发环境（devhome，不入仓库）

构建需要完整 devhome（含 arm64 node 运行时、dshroot、dshhome 等），通过 `export DSH_DEV_HOME=<路径>` 提供，
`build.sh` 会 source `$DSH_DEV_HOME/build/env.sh`（本机自备替身文件，PATH 用 MSYS 的 `/c/...` 形式）。
`payload.zip`（≈118MB）即从 devhome 组装：`runtime/ + dshroot/ + dshhome(→.dsh) + bin/ + rish/`。

## 四、架构与启动流程

```
APK (com.deepseek.harness)
├── MainActivity（原生壳，主题 AppTheme / AppTheme.Light 按系统深浅色 setTheme 二选一）
│   ├── 【权限引导页】首次启动：权限行 + 「开始使用」→ 解压运行时
│   ├── 【控制台】冷启动首页：解压状态（重新解压）/ 引擎 启动·重启·停止 /
│   │   授予权限 / 插件开关 / 日志查看分享 / 检查更新
│   ├── 【引擎页】WebView 加载 http://127.0.0.1:3080（DSH 原生界面）
│   └── applySystemBars()：状态栏/导航栏底色（FLAG_DRAWS_SYSTEM_BAR_BACKGROUNDS）
│       + refreshPageBackground() 用页面实测底色回填（沉浸）
├── OverlayService：小鲸鱼悬浮球（贴边吸附）+ 状态面板（状态/AI/端口 + 2×2 按钮）
├── VsreenBridgeService：桥 8999 → 特权核心 8998（Shizuku app_process 拉起），
│   预览悬浮窗：✕=销毁虚拟屏（/vscreen/close）、▾=收起到小鲸鱼（面板可叫回）
└── payload：node --expose-internals dsh/lib/bin.js web --host 127.0.0.1 --port 3080
```

要点：

- 引擎为**手动启动**（控制台「启动引擎」）；桥与核心随 App 启动自动拉起。
- 解压有 REVISION/.extracted/.complete 标记；「重新解压」删除标记走全量重写（25k 文件，数秒~数十秒）。
- `settings.yaml` / `.credentials.yaml` 属用户数据：解压与配置刷新均**不覆盖**（只在缺失时写入）。

### 主题与状态栏机制（重要，改主题前必读）

- **WebView 的 `prefers-color-scheme` 只由主题的 `android:isLightTheme` 决定，不看系统 uiMode**
  （Chromium `AwDarkMode.isAppUsingDarkTheme()` → `DarkModeHelper.getLightTheme()`）。
  框架只有 `Theme`(false) / `Theme.Light`(true) 声明它，因此壳必须按系统深浅在
  `Theme.Black.NoTitleBar`（AppTheme）与 `Theme.Light.NoTitleBar`（AppTheme.Light）之间 `setTheme()`。
- Holo 主题不设 `windowDrawsSystemBarBackgrounds`，`setStatusBarColor()` 会是**空操作**——
  必须显式 `addFlags(FLAG_DRAWS_SYSTEM_BAR_BACKGROUNDS)`（见 `applySystemBars()`）。
- 状态栏图标深浅按**底色亮度**（`isLightColor`）判定，不按系统深浅（用户可在前端手选主题）。
- 壳配色一律走 `colors.xml`（`cBg()/cText()/cSub()/cAccent()` 等入口），禁止在代码里写死十六进制；
  页面实测底色（`refreshPageBackground`）是运行时数据，不属于静态配色。

### 端口一览（v1.18 起按变体错开）

| 变体 | 引擎 | 通知(引擎+1) | 虚拟屏桥 | 虚拟屏核心 |

| official | 3080 | 3081 | 8999 | 8998 |
| lite | 3082 | 3083 | 9009 | 9008 |

| community | 3086 | 3087 | 9029 | 9028 |

每个变体一段独立端口 + 独立外部目录，**同一设备上多变体可同时运行**（含虚拟屏互不冲突）。

> 历史注记：旧共存线曾按包名派生端口（9009/9008），后一度退化为"硬编码 8999/8998 + contains() 猜目录"，
> 导致正式版与 Lite 的虚拟屏二选一；v1.18 重新按变体彻底错开。
> 无障碍截图目录 `screenshots/` 走 `<外部目录>/screenshots/`（不再硬编码正式版目录）。

### 定制面：哪些改动能活下来（B1①，v1.18 核对）

改运行中的 App 有两条路，**结果完全不同**：

| 定制方式 | 升级/重新解压后 | 依据 |
|---|---|---|
| 装插件（`dsh-plugin-manager`） | ✅ 存活 —— profile 清单是**合并**写入，不整文件覆盖 | `MainActivity.writeMergedProfileManifest` |
| 改 `profiles/web/cordis.patch.yml`（profile 补丁层） | ✅ 存活 —— 列为**用户文件**，只在缺失时写入 | `DSHHOME_USER_PATHS` |
| `settings.yaml` / `.credentials.yaml` / 会话数据 | ✅ 存活 | 同上 |
| 改 `dshhome/cordis.patch.yml`（home 层补丁） | ⚠️ 含 marker + 关键禁用项则保留；被改坏则从 payload 恢复 | `MainActivity.ensurePatchConfig` |
| 改 `dshroot/**` 内核 JS | ❌ 会被覆盖 —— 白名单文件每次同步都覆盖；其余文件在内核版本变化 / `.complete` 丢失 / 「重新解压」时全量重写 | `FORCE_OVERWRITE_PREFIXES`、`extractPayload` 各模式 |

**结论**：运行期定制请走 **profile 补丁 + 插件**（这两条能活）；
确实必须改内核代码的，写进 `dsh-patches/overlay/` 并用 `apply.sh` 重放，
同时把它加进 `FORCE_OVERWRITE_PREFIXES` 白名单，让它随 APK 正常下发到已升级设备。
「导出全部数据 / 从备份导入还原」可以在换包（签名/包名变化需卸载）时保住会话与配置。

### 设备端技能（D1）：AI 怎么知道"该怎么改自己"

- 真源在仓库 **`skills/<name>/SKILL.md`** → `build.sh` 打进 `assets/skills/` →
  壳启动时落到 **`<filesDir>/.agents/skills/<name>/SKILL.md`**
  （引擎的 `agentsHome` 默认 = `~/.agents`，HOME = filesDir；见 `dsh-skill-filesystem`）。
- 刻意**不放 payload**：`payload/dshhome/skills` 也是合法技能根，但 payload 会被解压/同步重写。
- 覆盖规则：文件不存在→写；含标记 `dsh-android-managed` 且内容变了→覆盖；**用户自己写的技能不动**。
- 改技能内容 = 改仓库 `skills/` + 重打包（`ensureAgentSkills()` 会在下次启动写回设备）。

### 区域截图与坐标契约（A6）

- `android_see` 支持 `select=<节点文字>`（按无障碍节点取景，可配 `pad`）与 `region="x,y,w,h"`；
  原生 `/screenshot` 同名参数，二者返回同一套几何。
- **坐标契约（唯一真源，改这里必须同步插件与文档）**：
  ```
  screenX = cropX + ix × scaleX        // ix/iy 是「裁剪图内」像素
  screenY = cropY + iy × scaleY
  cropX/cropY/cropW/cropH 均为屏幕坐标；scaleX = cropW / imageW
  整屏截图 == crop(0,0,screenW,screenH)，此时 scaleX/scaleY 与旧版语义完全一致
  ```
- 模型侧**不需要手算**：`android_tap/hold/swipe/touch/gesture` 支持 `ix/iy`（swipe/gesture 还有 `ix2/iy2`），
  插件按上面公式换算；没有几何时明确报错（不猜）。
- 为什么值得：模型侧网格投影会把整屏压到约 0.65× 线性；小块图会落入 `MIN_PIXELS=544×544` 的"小图"分支，
  几乎不被降采样 —— 同样的 token 预算下，区域截图的等效清晰度远高于整屏。

### 真机对话测试台（headless，无需 Web UI）

想验证"模型在真实会话里怎么用这些工具"时，不必走 WebView（一次性 token 不好拿）。做法是在设备上
另建一个**与 App 数据隔离**的 home，用 payload 里的 node 跑 DSH 自带的一次性入口：

```sh
# 1) 准备隔离 home（复制 App 的 dshhome 作为模板；不要写 App 自己的目录）
adb shell "mkdir -p /data/local/tmp/dshtest/home/profiles/headless"
adb shell "cp -r /data/user/0/<pkg>/files/payload/dshhome/. /data/local/tmp/dshtest/home/"

# 2) headless profile（bundles 换成 base + headless；cordis.patch.yml 必须是 []，否则会去找 web UI 插件）
#    profiles/headless/{cordis.yml=[], cordis.patch.yml=[], pnpm-workspace.yaml}
#    package.json: dsh.profile.bundles = ["@deepseek-ai/dsh-base","@deepseek-ai/dsh-headless"]

# 3) 运行器 run.sh 里设：
#    DSH_HOME/HOME=/data/local/tmp/dshtest/home
#    LD_LIBRARY_PATH=<payload>/runtime/lib ; PATH=<payload>/bin:<payload>/runtime/bin:$PATH
#    APP_A11Y_PORT=3187（指向 App 正在跑的无障碍服务）; DEEPSEEK_API_KEY=sk-…
#    node --expose-internals <payload>/dshroot/lib/node_modules/@deepseek-ai/dsh/lib/bin.js headless --json "<任务>"
```

`--json` 输出**结构化 transcript**（session / status+usage / thinking / text / tool_call / tool_result / final），
每行一个 JSON，可直接统计"工具调用次数、token、调用序列"。实测数据见 CHANGES 的「真机 agent 对话实测」一节。

### 免特权能力：列应用 / 启动应用（`android_apps` · `android_launch`）

壳内的本地路由（notify server，`POST` + JSON body；query 会被丢掉，参数一律放 body）：

| 路由 | 作用 | 鉴权 |
|---|---|---|
| `/shell` | 特权执行（Shizuku/App 进程通道） | token |
| `/setting` `/clipboard` `/usage` `/overlay` `/status` | 改设置 / 剪贴板 / 使用时长 / 悬浮窗 / 状态 | 无（`/usage` 靠系统权限门控） |
| **`/packages`** | 列出应用（`getInstalledApplications` + label + 能否启动），支持 `filter/third_party_only/launchable_only/limit` | token |
| **`/app`** | 启动应用（`getLaunchIntentForPackage` + `startActivity`） | token |

**为什么免特权可行**：本 App `targetSdk=28`，而 Android 11+ 的包可见性过滤**只对 targetSdk≥30 生效**，
所以 `PackageManager` 能看到/启动全部应用，**无需 `QUERY_ALL_PACKAGES`、无需 `<queries>`**。
⚠ 前提是 targetSdk 保持 28（本仓库因 node 的 noexec 限制必须如此）。**一旦提升到 30+**，
必须补 `<queries>`（`MAIN`+`LAUNCHER`）或 `QUERY_ALL_PACKAGES`，否则 `/packages` 会返回空列表。
参考：旧的 banyan MVP 仓库是 targetSdk 36，那里两者都声明了。

Android 10+ 有**后台启动 Activity 限制**：App 不在前台时 `startActivity` 可能被拦
（悬浮窗权限是系统豁免之一）。失败时错误信息会说明原因；要更强就授权 Shizuku/root 走 `am start`。

### payload 完整性清单（B9）：怎么发现"静默不一致"

- 打包期 `build.sh` 产出 `assets/payload_manifest.txt`（条目数/字节/`payload.zip` SHA-256/期望别名数/各子树统计）；
  `tools/build-apk.sh` 会核对清单与 `payload.zip` 实际值，不一致直接失败。
- 运行期 `MainActivity.checkPayloadIntegrity()` 核对 `runtime/`：
  非别名文件的**文件数与字节数**须与清单一致；别名须存在且与目标是**同一 inode**；
  结论写 `files/payload-integrity.txt` 并显示在控制台文件行。
- 顺带自愈：`applyLinks()` 发现别名与目标**不是同一 inode**（旧版实体化残留）时删掉重建为硬链/软链，
  免得升级用户一直背几十 MB 重复数据。

## 五、构建指南（Windows / Git Bash 实测）

```sh
cd android-app
export DSH_DEV_HOME="<devhome 的 Windows 路径>"
export ANDROID_JAR="/c/<SDK>/platforms/android-35/android.jar"   # sdk/android.jar 是空的，必须显式给
export JAVA_BIN="/c/<jdk-17>/bin"
export KEYSTORE_PASS=<密钥口令>            # release.jks 的口令；缺失会报错中止
export JAVA_TOOL_OPTIONS=-Dfile.encoding=UTF-8   # 否则 javac 按 GBK 读中文注释
bash build.sh                               # 产物 DeepSeekHarness.apk（已签名）
```

- ⚠️ **构建前 `unset MSYS_NO_PATHCONV`**：它会让 `jar`/`javac` 收到未转换的 `/d/...` 路径而失败。
  反过来，`adb push` 的设备路径要 `MSYS_NO_PATHCONV=1` 保护，且**本地路径写 `D:/...` 形式**
  （该变量同时关闭本地路径转换）。
- ⚠️ **Manifest 的 `<activity>` 属性列表中间不能放 XML 注释**：合法 XML 但 aapt 报
  `not well-formed`。注释放元素外面。
- 壳源码为 UTF-8 中文注释；新增 Java 代码**不要用 lambda/方法引用**（bootclasspath 下报
  LambdaMetafactory 找不到），用匿名内部类。
- 换密钥前先备份旧 `release.jks`；`apksigner verify --print-certs` 核对指纹再发布。

## 六、模拟器调试（x86_64 跑 arm64 引擎）

模拟器上 arm64 node 靠 `ndk_translation_program_runner_binfmt_misc_arm64` 转译执行，特殊步骤：

1. AVD 必须**带 `-writable-system` 启动**（ARM 库合并进 /system 的 overlay 存在 AVD 里，
   默认启动不挂载 → node 报 `library "libz.so.1" not found`）。
2. 每次（重）解压后，把 **x86_64 的三个裸名库** push 进 payload（备份自留）：
   `runtime/lib/libz.so`、`libssl.so`、`libcrypto.so`（转译器按裸名从 LD_LIBRARY_PATH 加载；
   node 本体依赖的是带版本号的 `.so.1`/`.so.3`，必须保持 arm64），并 `chown` 成 App 的 uid。
3. 冷启动后 Shizuku 服务端会丢，需用 adb 重新拉起（`libshizuku.so` 方式）。
4. 引擎日志：`files/dsh-web.log`（控制台「日志」可查看/分享）。
5. ABI 检查对非 arm64 设备 Toast 提示一次（SharedPreferences `abi_warned`），不弹模态框。

## 七、注意事项（踩坑记录）

1. **⚠️ targetSdk 必须保持 28**：≥29 时应用私有目录挂 noexec，node 执行报 EACCES。
2. node 运行需 `LD_LIBRARY_PATH=runtime/lib`；DSH 启动必须加 `--expose-internals`。
3. Android 无 `/usr/bin/env`，wrapper 脚本 shebang 用 `#!/system/bin/sh`；SELinux 禁 `link()`，原子写用 `rename()`。
4. `runtime/lib` 的软链 APK 里只打实体文件 + `LINKS.txt`，App 首次启动重建。
5. `pkill -f` 会误杀自己（命令行自匹配），用 `pkill -x node`。
6. Shizuku `pm install` 在部分 ROM（ColorOS）受 binder 限制；`pm clear/uninstall` 可用。
7. API Key 绝不写文件/APK；npm/pnpm 是开发工具，不进 APK。
8. DSH 更新会覆盖补丁和前端：更新后 `sh dsh-patches/apply.sh` + 重新构建；
   `FORCE_OVERWRITE_PREFIXES` 白名单控制强制覆盖项（插件/dist 补丁/dsh package.json）。
9. **原生 View 重复挂载崩溃**：`webView/statusView/progressBar` 是成员视图，切换界面先 `detachView()`。
10. **Shizuku 回调在 binder 线程**：更新 UI 必须 post 回主线程。
11. **不要用 `spawnSync` 执行耗时命令**：阻塞 node 事件循环 → 前端 "Failed to fetch"。
12. **ColorOS 电池优化会切断 Shizuku 连接**：App 与 Shizuku 都设「不限制」。
13. **WebView 主题/状态栏相关根因**见第四节；改壳配色只改 `colors.xml`。

## 八、插件开发路径

插件 = npm 包，核心 `ctx.tools.register(defineTool({...}))`：

1. 包放 `dshroot/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/<名>/`
2. 在 dsh 的 `package.json` dependencies 加包名
3. 在 `$DSH_HOME/cordis.patch.yml` 的 `insert:` 加 `- id: <名> name: '@deepseek-ai/<名>'`
4. 归档到 `plugins/<名>/`（并同步回 devhome 的 dshroot——仓库内 plugins 只是归档）

Shizuku shell（rish）调试：

```sh
DEX=/data/user/0/com.deepseek.harness/files/rish/rish_shizuku.dex
/system/bin/app_process -Djava.class.path="$DEX" /system/bin --nice-name=rish \
  rikka.shizuku.shell.ShizukuShellLoader -c "<命令>"
```

## 九、Shell 权限上限（无 root，Shizuku shell 模式，实测）

✅ 读 /system /vendor、读写 /data/local/tmp 与 /sdcard、pm/am/settings/dumpsys、input、screencap
❌ 其他 App 私有数据、/data/system、/system 分区、真 root
量产机上限即 shell；全文件访问需 root 或 userdebug 固件。
