# 引擎启动性能分析（2026-10-07，模拟器实测）

> 本文记录"引擎启动 ~30 s 到底花在哪、哪里能改、哪些已经试过"的**实测结论**，供后续优化与真机复测参考。
> 工具与复现命令见 [tools/boot-timing/README.md](../tools/boot-timing/README.md)。

## 0. 口径（先看这段，否则数字会被误读）

- **环境**：x86_64 模拟器（Pixel_10_Pro），社区版 `com.deepseek.harness.community`，版本 **1.17.5 / versionCode 54**，
  payload 为 arm64、经 **ndk_translation 翻译执行**（CPU 类开销被放大数倍）。
- **被测状态**：1.17.5 + 本分支的两处懒加载补丁（`dsh-tool-web`、`libreoffice-kit`）。
- **单次墙钟抖动很大**：`spawn → HTTP 就绪` 在同一版本连续 5 次是 **31 / 31 / 32 / 34 / 37 s**（26–37 s 区间）。
  所以**不要用单次墙钟判断优化效果**，要看下面这些内部指标。
- 计时探针本身约 +1–2 s 开销（同线程 `module.registerHooks` + `--cpu-prof`）。
- 模拟器上"裸 node 启动"实测 3.9 s、"内核 import + profile 合成（--dump-config）"累计 7.5 s（`bench-phases.sh`）。

## 1. 时间线分布

| 阶段 | 数值 | 依据 |
|---|---|---|
| 裸 node 启动（V8 + 内置模块） | **3.9 s** | bench-phases |
| 内核 launcher + profile 合成 | **7.5 s（累计，即 +3.6 s）** | bench-phases |
| **模块加载窗口**（首个→末个模块加载） | **26.4 / 29.2 s**（两轮） | hooks 内部时间戳 |
| ├ 读盘+transform（load 钩子） | **0.74–1.00 s（≈3%）** | hooks |
| └ 空档（解析/编译/链接/求值/DI） | **16.5–17.0 s** | hooks 差值 |
| 加载完毕 → HTTP 起监听 | ~2–4 s | 总时长 − 窗口 |

- 统计规模：**1,424 次模块加载**（141 内置 + **1,283 文件**）、源码 **12.5 MB**。
- 时间分布（十分位）：`79 15 291 219 167 193 10 249 179 22` → 加载**全程穿插**，无单一大停顿；
  最大单次空档 3.07 s（出现在 `picomatch` 之后）。

## 2. 归因分布（补丁后同一轮采样：37.2 s）

| 成分 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| **模块解析 resolve** | **5.16 s** | ~14% | 3,428 次，均值 1.50 ms，p95 3.8 ms（`getPackageScopeConfig` 0.71 / `URL` 0.65 / `realpathSync` 0.45 / `finalizeResolution` 0.37 / `deserializePackageJSON` 0.36） |
| **V8 解析/编译** | **≈5.0 s** | ~13% | `compileSourceTextModule` 2.27 + `compileForInternalLoader` 1.12 + `wrapSafe` 0.79 + V8 parse 0.81 |
| **cordis 挂载 / 依赖注入** | **6.55 s** | 17.6% | `cordis` 5.05（`get` 1.53）+ `plugin-loader` 1.50（`entries` 0.82） |
| **profile 合成 / schema / YAML** | **4.06 s** | 10.9% | `dsh-app-boot` 1.45 + `js-yaml` 1.10 + `schemastery` 0.85 + `zod` 0.67 |
| **文件 I/O（主线程）** | **4.31 s** | 11.6% | 含 `writeFileSync` **0.71 s**❗、`realpathSync` 0.45、`readFileSync` 0.36 |
| GC + native | 1.89 s | 5.1% | GC 0.97 |
| 其它 node 内部 / 插件自身 | 余量 | ~36% | 含 `dsh-tools` 0.82、`ds-harness-remote` 0.56 |

> 这些分类**互有重叠**（resolve/编译/求值都发生在"空档"里），不要相加当作总时长。

## 4. 可以改进的地方（按实测潜力排序）

| # | 手段 | 实测潜力 | 代价/风险 | 状态 |
|---|---|---|---|---|
| **A** | **从 profile 移除 OTel 三条目**（`dsh-host-product-telemetry-otel` / `dsh-session-telemetry-otel` / `dsh-otel`），必要时删除 `@opentelemetry/*` 包 | **2–3 s**（303 个模块 / 23.6% / ~1 MB） | 低（配置层；但属产品决策） | **未做** |
| **B** | **首启预热引擎**：向导期间不只是预热文件，也把引擎拉起来 | 感知 **33 s → ~3 s** | 低（需处理"未授权先起引擎"） | **未做** |
| **C** | `execa` 改为按需 `import()` | **0.5–1 s**（109 模块 / 309 ms 解析） | 中（多处 spawn 调用点） | **未做** |
| **D** | 把"小文件多"的依赖打包成单文件（semver / zod / pi-ai 等） | **0.5–1.5 s**（直接削 resolve 的 5.16 s） | 中高（改 vendor 字节与 ESM 结构） | **未做** |
| **E** | 查清启动期 `writeFileSync` 0.71 s 是谁在写（日志/状态？） | 待定 0.2–0.7 s | 低（先加 profile 的"调用者"视图） | **未做** |
| **F** | **真机 arm64 复测**同一套指标 | 不省时间，但决定优先级（模拟器放大 CPU 项） | 低 | **未做** |

**A 的关键前提（实测得出）**：OTel 那 300 个模块**即使插件条目被 `disabled` 也照样加载** ——
三个遥测插件的模块**静态 import** `@opentelemetry/*`，而 cordis 求值 `disabled` 条件前必须先 import 模块。
所以只能**移除 profile 条目**（`dsh-web-app/cordis.patch.yml`，可走 overlay），禁用无效。

## 5. 已经试过的（含失败项，避免重复踩）

| 手段 | 结果 |
|---|---|
| ✅ **懒加载 turndown/domino + fontkit/brotli**（本分支 `6778ee2`） | 模块加载跨度 **29,386 → 26,433 ms（−2.95 s）**；模块数 1519 → 1426（−93）；turndown/domino/fontkit/brotli/joplin 启动期 **0 次**加载 |
| ✅ 载荷 sha256 闸门（1.17.5 已有） | 每次启动 App 侧 **5.28 s → 0.11 s** |
| ✅ 向导期间预热解压（1.17.5 已有，`十五之二`） | 首启把 **~11.7 s** 解压藏进读向导的时间；「开始使用 → 主界面」≈33 s（只剩起引擎） |
| ✅ 内核树放内部存储（早前 v1.5.3） | 真机从 **50–60 s** 降到 ~10 s 量级（避开了 /sdcard FUSE 的 2 万次 stat/read） |
| ✅ 引擎慢启动不再判失败（1.17.5，`b48e8f7`） | 90 s 单次超时 → **进程健在时最多再等 4×90 s** |
| ✅ 前端故障回退（1.17.5，`十五之三`） | 白页 8 s 探针 / 主框架重试 12×2.5 s / 卡启动壳 45 s → 落控制台 |
| ❌ **`NODE_COMPILE_CACHE`（V8 字节码缓存）** | **无收益**：热缓存下 `import turndown` 984→990 ms、`import fontkit` 1458→1330 ms（~9%，噪声级）→ 不再考虑 |
| ❌ **V8 快照 / SEA** | 架构不可行：Node 快照只支持单入口、不能加载额外用户模块，与 cordis 运行时动态挂载冲突 |
| ❌ 把第三方依赖打成单文件（上一轮判断"收益有限"） | 该判断基于 **2.5 s 的估算**；现在 resolve **实测 5.16 s**，应重新评估（见 D） |
| ❌ 跨线程 `module.register()` 做计时 | 探针自身让 33 s 变 44 s（主线程 `makeSyncRequest` 11.2 s）→ 方法学教训；改用同线程 `module.registerHooks()` |
| ✅ `--trace-sync-io` | 启动期**零告警** → 主线程没有同步 I/O/同步外部命令，空档确属 CPU |

## 6. 懒加载的收益与代价（本次唯一落地的优化）

**收益（实测）**：模块加载跨度 −2.95 s（29.4 → 26.4 s）；少加载 93 个模块（12.5 MB 里少 ~1.4 MB）；
读盘 −206 ms；≥50 ms 空档 −1,225 ms。同插桩口径：**34 s → 31 s**。

**代价**：
- 首次 `web_fetch` 多 ~1.0 s，但**与网络抓取并行**（`Promise.all`），实际无感；之后常驻内存；
  极端情况（抓取 <1 s 且正文是 HTML）该次会走原有"HTML content omitted"兜底（不崩）；
- 首次文档渲染多 ~1.4 s，但落在 **Worker 线程**（`font-snapshot-worker.js` 自带 `import fontkit`）；
- 多维护 2 个上游补丁文件（overlay 现 39 文件，内核升级要跟着重采）；
- **改上游代码有风险**：本轮曾因漏一个闭合括号导致 `tool-web never started`、会话建不起来
  （详见 §7），已加预检门。

## 7. 事故记录与防线（2026-10-07）

**事故**：给 `dsh-tool-web` 打懒加载补丁时，`turndown.addRule` 的三处调用只包住了一处，
函数闭合括号放早 → 运行期 `ReferenceError: turndown is not defined` → 插件挂载失败 →
用户侧 `New session failed: agent-preset/invalid: tool-web: never started`。已修复并验证。

**为什么两道检查都没拦住**：
1. 我用了 `node --check` —— **它不解析 ESM**（对 `.mjs`/`type:module` 的 `.js` 按 CJS 解析），
   所以"语法 OK"是假结论（后来真解析器报出 `Unexpected token 'export'`）；
2. 我检查的是**设备上尚未替换的旧文件**；
3. overlay 副本没跟内核树同步，仓库里躺着中间那版坏文件。

**现在的防线**（推补丁/提交前必跑）：
- [tools/overlay-preflight.sh](../tools/overlay-preflight.sh)
  ① 真 ESM 解析：[tools/esm-parse-check.mjs](../tools/esm-parse-check.mjs)（`vm.SourceTextModule` 只解析不执行）；
  ② **设备侧真实 `import`**：抓 `--check` 抓不到的求值期错误（浏览器侧 `lib/client.js` 会被排除）。
- [tools/overlay-drift.sh](../tools/overlay-drift.sh)：overlay 与内核树必须逐字节一致（当前 39/0/0）。
- [tools/overlay-recapture.py](../tools/overlay-recapture.py) `--write/--prune`、[tools/overlay-normalize-lf.py](../tools/overlay-normalize-lf.py)。

## 9. 复现方法

见 [tools/boot-timing/README.md](../tools/boot-timing/README.md)：
```
推工具到设备 → 跑 plain / hooks / profhooks / sync 四种模式 → 拉产物 → analyze.py 出报告
```
关键坑（都写在 README 里）：不要用跨线程 `module.register()` 计时；`--cpu-prof` 需正常退出才落盘；
`date +%s%N` 在 Android toybox 上不可用。
